# ShareSDK 调研与 OpenShare 的取舍

日期：2026-11-09。状态：调研结论与下一版设计建议；新接口尚未实现。

阅读顺序：[协议分析](protocols.md) → [新 SDK 设计](../next-sdk/design.md) → [验证与迁移](../next-sdk/validation.md)。所有外部事实的出处及读取限制见[来源目录](sources.md)。

## 结论

OpenShare 可以继续保持“小核心、少依赖、简单调用”。下一版应统一**操作语义和能力描述**，在底层组合系统分享、公开链接、标准浏览器认证和按需厂商适配器。对于尚无公开稳定契约的客户端协议，先保留独立研究入口，取得指定版本的互通证据后再纳入稳定支持。

ShareSDK 是有价值的接口与平台覆盖参考，但公开证据不支持“它有一个所有平台通用的底层协议”或“去掉官方 SDK 后所有功能照常工作”这两个判断。反过来，也不能把所有分享和登录都判定为必须依赖厂商 SDK：Android 微信模块确实包含自有 IPC 模型与传输实现，是独立协议路线的具体证据。[M02](sources.md#m02)、[M06](sources.md#m06)。

## 实际核对的对象

| 对象 | 核对范围 | 能得出的结论 |
| --- | --- | --- |
| ShareSDK 产品页 | 分享、登录、短链、统计和回流功能说明 | 产品定位；“40+”不代表每个平台支持每种能力 |
| CocoaPods `mob_sharesdk` 4.4.51 | 版本化 podspec、分发 ZIP 目录、当前公开头文件 | 当前该渠道的依赖与 API 结构 |
| MobClub iOS 仓库 | 固定提交，仓库 spec 版本 4.4.23 | 历史组织结构；不能代替 4.4.51 |
| MobClub Android 仓库 | 固定提交的平台配置和示例 | 按平台注册、按需接入；示例 App 版本不作为 SDK 版本 |
| ShareSDK Android 3.10.36 | 官方 Maven 元数据、POM、Core AAR 与微信/QQ/微博模块 JAR | 确认该渠道版本，以及微信等模块的自有协议实现线索；未验证完整运行依赖图 |
| 腾讯 SDK / 微博官方仓库 | 指定版本的头文件或模型序列化 | 凭证形态、SDK 公共入口，以及部分实现层字段 |
| OS 文档和 OAuth/OIDC 标准 | 分享、回调、浏览器认证、令牌校验 | 可复用的稳定基础机制 |

没有测量 ShareSDK 的最终 App 增量、启动性能、离线可用率或实际网络采集。没有用公开 demo 里的密钥测试登录，也没有给本报告所列平台都完成真机验收。

## ShareSDK 统一了什么

当前 iOS 公开头文件把授权、用户资料与分享放在统一入口下，返回 session，并通过状态回调通知调用方；平台配置另有注册入口。WeChatConnector 还允许应用接管授权码换 token 的步骤。这说明通用抽象和业务服务端可以分离。[M02](sources.md#m02)。

可借鉴：统一调用习惯、平台注册、分享面板与底层通道分离、错误分类、授权与资料获取分离。需要重新设计：类型安全的内容模型、精确能力判断、凭证类型、回调关联、取消/超时语义，以及不同平台能提供的结果证据。

### 标准包、Lite 包与原生 SDK

4.4.51 podspec 的实际配置如下；这只说明声明的分发组成：

| 模块 | 平台 connector | 随模块声明的厂商二进制 |
| --- | --- | --- |
| WeChat / WeChatFull | 有 | 微信 XCFramework；Full 使用另一支付相关分发目录 |
| WeChat_Lite | 有 | 该 subspec 未声明附带微信二进制 |
| QQ / QQ_Lite | 都有 | 标准模块附带 TencentOpenAPI，Lite 未声明附带 |
| SinaWeibo / SinaWeibo_Lite | 都有 | 标准模块附带微博制品，Lite 未声明附带 |
| Douyin / XHS | 有 | 分别声明抖音、小红书官方制品 |
| ShareSDK 基础依赖 | — | 声明 MOBFoundation 依赖 |

Lite 的能力、是否需宿主另行链接 SDK、是否存在 Web/系统降级、哪些客户端版本适用，都要另外确认。不能仅凭包名或依赖缺失断言“独立复刻完整原生协议”。本次没有对 Lite 包进行运行或网络实测。[M02](sources.md#m02)。

Android 不能照搬上述 iOS 分发结论。3.10.36 的微信 Core 有自己的媒体模型、消息封装及传输/返回处理；QQ 和微博模块也能观察到各自原生路由。这说明研究独立协议有实际依据，但既不证明 iOS Lite 行为相同，也不证明拷出一个 JAR 就能摆脱 Mob 公共依赖独立运行。[M06](sources.md#m06)。

### 它不是纯离线转发库

产品范围包含短链与回流统计，接入也有 Mob 自身的应用配置。由此可以确认它承担了本地转发之外的产品职责；不能进一步推断每次分享必定访问哪些服务器。[M01](sources.md#m01)。

OpenShare 的默认设计不需要自己的云账号、统计服务器或短链服务。需要这些能力时通过显式扩展接入，由宿主选择服务商。系统分享和公开链接不应被自有云服务的可用性阻塞。

## 按原来的思路，哪些可以继续精简

| 路径 | 能否不带厂商 SDK | 限制 |
| --- | --- | --- |
| iOS activity / Android Sharesheet | 可以 | 不能保证指定社交 App 出现、指定朋友圈目的地或最终发布回执 |
| 平台公开的 HTTPS 分享入口 | 可以，按已确认入口逐项支持 | 通常限文字/链接；调起或打开页面不是发送成功 |
| 明确允许原生公共客户端的 OAuth + PKCE | 可以，不强制使用聚合商 SDK | 提供方必须实际支持相应注册、回调和授权模式 |
| Apple 系统登录 | iOS 可直接用系统框架 | Android 需要独立的网页/服务端配置 |
| 微信/QQ/微博等原生定向功能 | 可研究自有 wire adapter；已有官方适配器可作过渡与对照 | Android 已有静态实现线索，完整互通和 iOS 对应路径仍须逐项验证 |
| 平台私有 IPC | 技术上可研究 | 必须有版本范围、校验机制、测试数据及回归维护，不能只修改 `sdkver` 字符串 |

这保留了原 OpenShare 对体积和调用简洁性的追求，也给协议实现留下可替换的位置。选择官方适配器属于当前有证据的交付路径，并不等于设计上禁止后续独立协议适配器。

## 与当前 PR 的关系

当前实现已经有系统分享和可选微信官方适配器，适合作为第一批 provider。它还没有下面设计中的能力计划、统一授权凭证、持久化回调路由或完整的跨平台状态机。

现有旧 category 仍在默认 iOS 包中，不能把这一点延续成新版默认设计。下一版应将旧协议隔离成显式 Legacy 模块，并提供迁移兼容层；不在本轮调研中静默删除旧接口或改写其行为。

## 建议的交付范围

第一阶段先把系统分享、公开链接、已有微信路径纳入统一契约，并补齐登录验证接口与测试夹具。独立协议研究优先从证据较充分的 Android 微信开始：先做编码对照和单平台互通，再扩至 iOS、QQ、微博；已有官方适配器保留作过渡。抖音、Apple、Google 按实际项目需求进入下一阶段。小红书和其他合作/权限受限平台在获得接入资格、确认能力后再承诺支持。

首版不承诺同时复刻 ShareSDK 的 40+ 平台、统计后台、好友关系和短链业务。平台清单可以扩展；一个平台是否支持登录、分享、某种媒体、某个渠道及何种回执，应分别列明。
